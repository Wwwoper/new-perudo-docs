# Perudo — продуктовые сценарии и границы первого релиза

Версия: 1.0
Статус: рекомендуемый продуктовый контракт для первого релиза; не определяет UI-фреймворк, БД или способ развёртывания.

## 1. Цель документа

Связать уже согласованные доменные и учебные контракты с пользовательскими сценариями. Сценарии ниже описывают ожидаемый результат и ограничения, а не конкретные экраны или технологическую реализацию.

Основание: контракты Game Domain, S2–S4, Learning Core и межмодульная архитектура; UX-аудит семи экранов. UX-аудит выполнен по статичным скриншотам, поэтому выводы о фактическом поведении интерфейса требуют отдельной проверки.

## 2. Рекомендуемый объём MVP

Включить:

1. Обучение навыкам S1–S9 через отдельные упражнения и последовательности упражнений.
2. Тренировочные ситуации Perudo с точными расчётами там, где они предусмотрены контрактами S3/S4.
3. Объяснение результата, исправление после feedback, завершение упражнения и обзор эталона.
4. Историю попыток и прогресс по отдельным навыкам.
5. Простые прозрачные рекомендации следующего упражнения и повторения.
6. Локальную реальную партию по согласованным правилам Perudo Classic.

Не включать в MVP без отдельного решения:

- сетевую игру между удалёнными игроками;
- синхронизацию прогресса между устройствами;
- социальные функции, рейтинги и публичные профили;
- ML-персонализацию;
- совместное редактирование/обмен пользовательскими сценариями;
- серверную защиту эталона как обязательное свойство первого релиза.

**Рекомендация по профилю пользователя:** начать с одного локального учебного профиля на устройстве без обязательной регистрации. Использовать устойчивый внутренний `user_id`; не собирать имя, email и иные персональные поля, пока не появится конкретный сценарий синхронизации или восстановления профиля. Это продуктовая рекомендация, а не уже согласованное требование.

## 3. Основные пользовательские сценарии

### PS-01. Первый запуск и знакомство

**Цель:** пользователь понимает назначение приложения и может начать первое упражнение без изучения всей справки.

Основной поток:

1. Приложение создаёт или загружает локальный профиль.
2. Показывает краткое объяснение формата обучения и предлагает начать вводное упражнение.
3. Пользователь выбирает «Начать»; подробные настройки остаются вторичными.
4. Application получает план, создаёт и сохраняет упражнение, затем явно начинает попытку.
5. Пользователь получает только PublicExercise.

Альтернативы:

- если генерация не удалась, пользователь получает понятную возможность повторить действие; ошибка не записывается как ошибка ученика;
- если упражнение уже создано, но ответ на запрос потерян, повтор с тем же `operation_id` возвращает тот же экземпляр;
- предварительно загруженное, но не начатое упражнение не создаёт ExerciseAttempt.

Критерии приёмки:

- первое упражнение можно начать без настройки порогов и чтения длинной справки;
- показ невозможен до сохранения экземпляра;
- повтор запроса не создаёт дубликат упражнения или попытки.

### PS-02. Прохождение одного упражнения

**Цель:** пользователь выполняет один конкретный шаг и понимает ожидаемое действие.

Основной поток:

1. Экран показывает цель/навык, краткую инструкцию, ситуацию и один явный вопрос.
2. Пользователь вводит типизированный ответ или выбирает действие.
3. Система сохраняет AnswerSubmission до проверки.
4. Evaluation проверяет ответ по сохранённой версии критериев.
5. Пользователь получает основную ошибку/успех и краткое объяснение.
6. Только после feedback разрешается следующая отправка/исправление.

Критерии приёмки:

- в каждый момент ясно, что требуется сделать;
- некорректный формат ответа отличается от неправильного по содержанию;
- повторная отправка после технического сбоя не дублирует метрики;
- пользователь не получает полный эталон до завершения всего упражнения.

### PS-03. Многошаговое упражнение и исправление

**Цель:** пользователь может исправить рассуждение, не теряя историю предыдущих попыток.

Основной поток:

1. Упражнение содержит несколько обязательных и optional шагов.
2. Каждый ответ сохраняется отдельной отправкой.
3. После каждой отправки предоставляется feedback по основной ошибке.
4. Исправление доступно после feedback; предыдущие отправки остаются неизменяемой историей.
5. Partial/follow-through credit учитывает корректные последующие шаги, если это предусмотрено критериями.
6. Optional шаги не блокируют завершение и не снижают обязательный итоговый балл.
7. После завершения показывается полный разбор и эталон.

Критерии приёмки:

- история отправок сохраняет порядок и результат каждой проверки;
- завершение невозможно при незавершённом обязательном шаге;
- завершение возможно при пропущенных optional шагах;
- повторный CompleteAttempt идемпотентен.

### PS-04. Подсказка и самостоятельность

**Цель:** подсказка помогает продолжить обучение, но не маскирует самостоятельность ответа.

Основной поток:

1. Пользователь открывает подсказку по запросу.
2. Система фиксирует факт и тип подсказки в рамках попытки.
3. Пользователь отправляет ответ.
4. Learning Progress хранит correctness и hint usage раздельно.

Критерии приёмки:

- факт подсказки не меняет EvaluationResult автоматически;
- метрика independent accuracy учитывает использование подсказки по отдельному правилу;
- подсказка не раскрывает закрытый эталон.

### PS-05. Завершение и просмотр разбора

**Цель:** пользователь видит результат всего упражнения и понимает, что делать дальше.

Основной поток:

1. Application проверяет обязательные completion criteria.
2. Learning Progress переводит попытку в COMPLETED и обновляет метрики/состояние навыка.
3. Только после подтверждённого завершения Exercise Engine выдаёт ExerciseReviewView.
4. Feedback формирует итоговое объяснение.
5. Learning Strategy предлагает следующее упражнение или повторение.

Критерии приёмки:

- до COMPLETED полный эталон недоступен;
- после завершения повторное открытие разбора не меняет прогресс;
- рекомендация не блокирует свободный выбор следующего действия.

### PS-06. Продолжение после закрытия приложения или сбоя

**Цель:** пользователь не теряет уже подтверждённые действия.

Рекомендуемое поведение:

- попытка в STARTED/IN_PROGRESS открывается повторно по тому же `attempt_id`;
- неподтверждённая операция не отображается как успешно завершённая;
- отправка в RECEIVED без результата продолжает обработку по тому же `submission_id`;
- отправка в EVALUATED, но ещё не применённая к Progress, идемпотентно применяется;
- состояние COMPLETED/ABANDONED не возвращается в активное;
- пользователь может явно отказаться от продолжения, если это разрешено состоянием.

Критерии приёмки:

- ни одна подтверждённая отправка не исчезает;
- восстановление не создаёт дублирующих submission, completion или review tasks;
- при невозможности безопасного восстановления пользователь получает явную ошибку, а данные не переписываются молча.

### PS-07. Повторение и рекомендации

**Цель:** пользователь практикует слабые/забываемые навыки и видит причину рекомендации.

Основной поток:

1. Learning Progress предоставляет SkillProgress, ErrorStatistics и ReviewTask.
2. Learning Strategy выбирает навык, тип и сложность упражнения по прозрачным правилам.
3. Пользователь может принять рекомендацию или выбрать другой навык.
4. Повторение создаёт новый Exercise и новый ExerciseAttempt, а не переоткрывает старую попытку.
5. ReviewTask закрывается/обновляется идемпотентно по результату.

Критерии приёмки:

- объясняется причина рекомендации: повторение из-за интервала, ошибки или закрепления;
- рекомендации не являются жёсткой блокировкой;
- нет общего рейтинга/уровня пользователя вместо отдельных навыков.

### PS-08. Сброс прогресса навыка

**Цель:** пользователь может начать освоение навыка заново, не уничтожая историю.

Основной поток:

1. Пользователь выбирает конкретный навык и подтверждает сброс.
2. Learning Progress сбрасывает текущую проекцию/статус по принятой политике.
3. История попыток и переходов статуса сохраняется.
4. Learning Strategy строит рекомендации на основании состояния после сброса и допустимой истории.

Критерии приёмки:

- действие явно ограничено одним навыком;
- до подтверждения показано, что история не удаляется;
- сброс не эквивалентен удалению пользовательских данных.

### PS-09. Локальная партия Perudo

**Цель:** пользователь проводит партию по согласованным правилам.

Основной поток:

1. Создать партию на 2–6 участников и выбрать/подтвердить правила.
2. Начать партию, выполнить броски и показывать игроку разрешённое представление.
3. Принять ставки и отдельный переход хода.
4. Обработать Dudo атомарной последовательностью доменных событий.
5. Сохранить партию и историю; восстановить её после закрытия приложения.
6. Завершить партию при одном активном участнике.

Критерии приёмки:

- закрытые значения чужих кубиков недоступны до допустимого раскрытия;
- выбывшие остаются видимыми, но не участвуют в очереди и расчётах;
- BID_PLACED и TURN_ADVANCED не смешиваются;
- Dudo и последствия применяются атомарно;
- повтор команды с тем же ID не меняет состояние второй раз.

## 4. Общий UX-контракт учебного экрана

UX-аудит выявил перегруженность справкой, неочевидность требуемого действия, конкурирующие числовые показатели и нестабильность структуры экранов. Поэтому для всех типов упражнений рекомендуется общий порядок смысловых зон:

1. раздел/навык и цель;
2. короткая инструкция — одно основное действие;
3. ситуация и необходимые данные;
4. область ответа;
5. результат с коротким выводом;
6. дополнительное объяснение/подсказка по запросу;
7. следующий шаг.

Правила:

- подробная теория не конкурирует с задачей; она сворачивается или показывается по запросу;
- сначала вывод человеческим языком, затем проценты/формулы/детали;
- «безопасная ставка» не используется без явного объяснения, что это вероятностный порог, а не гарантия;
- текущая ставка визуально отделена от истории торгов;
- интерфейс не полагается только на цвет для передачи статуса;
- один главный CTA на каждом состоянии экрана;
- одинаковые понятия имеют одинаковые названия во всех режимах.

## 5. Сценарии, не определённые текущими источниками

Не делать вид, что следующие вопросы уже согласованы:

- нужна ли регистрация, вход, несколько профилей и восстановление профиля;
- нужен ли облачный backup, синхронизация или перенос между устройствами;
- какие платформы и режимы доступности обязательны;
- нужны ли экспорт/удаление всего профиля и срок хранения учебной истории;
- кто является целевой аудиторией по возрасту и нужны ли родительские функции;
- нужны ли аналитика использования и телеметрия.

Рекомендация MVP: не реализовывать эти функции, пока конкретный пользовательский сценарий не требует их. До появления регистрации не собирать email/имя; до появления синхронизации не вводить облачный профиль.
