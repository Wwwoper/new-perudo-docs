# ADR-013: Runtime для доменной и учебной логики в browser-only приложении

- **Статус:** PROPOSED — DECISION OPEN
- **Дата:** 2026-11-09
- **Владелец решения:** Product/Technical owner — TBD
- **Связанные документы:** `final-mvp-implementation-handoff.md`, `implementation-handoff-readiness.md`, `architecture/README.md`

## Контекст

Текущий продуктовый baseline задаёт web desktop/mobile, browser-only local-first, один локальный профиль, отсутствие обязательного backend и offline после первого успешного открытия. Логическая архитектура разделяет Game Domain, skills, exercise, evaluation, progress, strategy, presentation и application.

При этом документация не фиксирует физический runtime для доменной и учебной логики. Ранние упоминания Python-пакетов не являются выбором технологии. Наличие Python в навыках разработчика также не является архитектурным доказательством.

## Рассматриваемые варианты

### A. TypeScript как runtime приложения

Доменная логика, генераторы, evaluator и browser integration реализуются на TypeScript; Python может оставаться языком вспомогательных offline tooling/scripts, если это потребуется отдельно.

**Преимущества:** нативная интеграция с браузером, IndexedDB, Service Worker и UI; единый runtime и простая offline-доставка; меньше runtime-слоёв.

**Издержки:** доменные и математические контракты нужно реализовать на TypeScript; если существующие эталоны/алгоритмы написаны на Python, потребуется перенос и независимая проверка эквивалентности.

### B. Python в браузере через WebAssembly runtime (например, Pyodide)

Доменная и часть учебной логики выполняется в Python runtime, загружаемом в браузер.

**Преимущества:** повторное использование Python-кода и знакомого языка; возможность сохранить единый язык для математического ядра и tooling.

**Издержки:** дополнительный runtime и размер загрузки; время старта и память; интеграционная граница Python↔JavaScript; ограничения доступности пакетов и браузерных API; отдельная проверка cold-start/offline/cache поведения.

### C. Гибрид

TypeScript отвечает за UI, persistence и browser lifecycle; Python/WASM — за выбранное вычислительное ядро.

**Преимущества:** можно повторно использовать Python только там, где это оправдано; browser API остаются в нативном runtime.

**Издержки:** два runtime, сериализация DTO, границы ошибок и версий; сложнее тестировать и отлаживать, чем один runtime.

## Критерии выбора

Решение должно сравнить варианты на одном и том же вертикальном срезе (S3/S4 calculation + deterministic fixture + offline reload), по следующим критериям:

1. Offline cold start после первого успешного открытия и поведение при очистке cache.
2. Размер первоначальной и последующей загрузки.
3. Время старта runtime и задержка типичного exercise flow на целевых desktop/mobile браузерах.
4. Доступность и надёжность IndexedDB, Service Worker и backup/import без обходных слоёв.
5. Детерминизм, точность Fraction/binomial vectors и отсутствие расхождения с нормативными контрактами.
6. Возможность тестировать домен независимо от UI и браузера.
7. Поддерживаемость, доступность библиотек и стоимость обновления runtime.
8. Простота интеграции, диагностики и миграции данных.

## Рекомендация для оценки

Сначала выполнить небольшой технический spike для вариантов A и B на одинаковом вертикальном срезе; вариант C рассматривать только если измеримое преимущество оправдывает второй runtime. Это рекомендация по способу принятия решения, а не утверждение, что какой-либо вариант выбран.

## Последствия до принятия решения

- Статус выбора языка/runtime остаётся OPEN.
- Нельзя указывать Python/WASM или TypeScript как утверждённый стек в README, roadmap или implementation tasks.
- Логические контракты и тест-векторы остаются независимыми от языка.
- Нельзя объявлять I-1 полностью implementation-ready, если конкретный этап требует runtime-зависимого кода.
