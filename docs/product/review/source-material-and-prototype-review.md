# Ревизия приложенных материалов и прототипов Perudo

**Статус:** аналитический review входных материалов; не является утверждением правил или приёмкой реализации.

## 1. Объём и ограничения ревизии

Рассмотрены материалы, переданные вместе с текущим этапом:

- `perudo_trainer.html` — автономный HTML-тренажёр вероятностей и подсчёта;
- семь статичных изображений `0001.png`–`0007.png` — экраны другого/более широкого учебного интерфейса.

HTML прочитан как исходный код. Изображения рассмотрены как визуальные свидетельства. По статичным изображениям нельзя подтвердить реальную навигацию, адаптивность, доступность, сохранение состояния, вычислительную корректность или поведение элементов управления. Не предполагается, что изображения и HTML относятся к одной версии продукта.

## 2. Что подтверждают материалы

### 2.1 HTML-тренажёр

Видимый сценарий HTML ограничен задачами подсчёта и вероятности:

- генерация руки игрока, общего числа кубиков и заявки;
- отдельные режимы ставки на грань 2–6 и на единицы;
- вычисление собственных совпадений и числа неизвестных кубиков;
- оценка вероятности события «не меньше нужного числа»;
- режим определения максимальной заявки по заданному порогу;
- точные таблицы для вероятностей 1/3 и 1/6;
- приближённая ментальная оценка;
- локальный счётчик правильных полей.

Это подтверждает наличие узкого учебного прототипа для части S3/S4 и элемента решения, близкого к S8. Это не доказывает покрытие всех сценариев этих навыков и не подтверждает готовность S1, S2, S5–S7 или S9.

### 2.2 Статичные экраны

На изображениях видны несколько учебных представлений и режимов: оценка вероятности/решения, правила единиц, чтение закрытой информации, последовательность ставок, оценка по нескольким параметрам и серия ситуаций. Это полезные визуальные референсы для структуры упражнения и объяснения ответа.

Изображения не являются достаточным источником для утверждения точных правил ставок, критериев корректности, порогов мастерства, порядка событий или правил Palifico. Текст, который невозможно надёжно прочитать на изображении, не переносится в нормативные документы.

## 3. Наблюдения по HTML, требующие продуктового решения или технической проверки

| ID | Наблюдение | Риск / влияние | Рекомендация для MVP |
|---|---|---|---|
| SRC-01 | Порог «верю / не верю» в режиме заявки равен 40%, а порог максимальной заявки — 55% | Это две разные конвенции упражнения, а не единое правило игры или универсальная стратегия | Сохранить только как явные параметры конкретного упражнения; показывать смысл порога до ответа |
| SRC-02 | Быстрая прикидка включается при 6+ неизвестных кубиках и допускает диапазоны приблизительных ответов | Прикидка может расходиться с точной вероятностью; диапазоны являются учебной аппроксимацией | Не использовать приближённый ответ как эталон математической точности; отдельно оценивать понимание диапазона |
| SRC-03 | В HTML вероятности рассчитываются числами с плавающей точкой через биномиальную сумму | Для отображения может быть достаточно, но это не реализует контракт точной арифметики `Fraction` | Для нормативного S4 эталон и вычисление должны опираться на точную дробь; HTML считать демонстрационным, пока не проверен отдельно |
| SRC-04 | Поля ввода не задают явные минимумы/максимумы, целочисленность и валидацию диапазонов | Можно вводить отрицательные, дробные или заведомо невозможные значения; некорректные значения попадают в проверку | Добавить граничную валидацию и сообщения до оценивания; проверить NaN и значения вне диапазона |
| SRC-05 | Счётчик `ok/all` увеличивается при каждом вызове проверки и считает поля, а не независимые экземпляры | Повторные проверки могут искусственно увеличить знаменатель и число правильных ответов; счёт не эквивалентен mastery evidence | Не переносить этот счётчик в Learning Progress; сохранять submissions и first/final correctness отдельно |
| SRC-06 | Повторное нажатие «Проверить» снова добавляет все поля к счётчику | Одна и та же попытка многократно учитывается | Идемпотентно фиксировать отправку либо присваивать отдельный submission ID каждому действию с явной семантикой |
| SRC-07 | `best()` выбирает максимальную заявку по фиксированному порогу 55% | Формулировка «безопасная ставка» может восприниматься как объективная гарантия | Использовать нейтральное название «максимальная заявка при пороге X%» и объяснять условность критерия |
| SRC-08 | В HTML отсутствует отдельный режим Palifico | Расчёты с p=1/3 и p=1/6 не покрывают все правила и параметры режима | Не расширять этот прототип на Palifico без отдельного утверждённого контракта и тестовых примеров |
| SRC-09 | Локальная тема сохраняется в `localStorage`, но попытки и прогресс не сохраняются | Демонстрационный счёт теряется при перезагрузке; отсутствует жизненный цикл попытки | Не считать HTML доказательством соответствия local-first, восстановления и backup требований |
| SRC-10 | Результат формируется HTML-строками; в сценарии ввода нет явного разделения первичной ошибки, подсказки и раскрытия эталона | Модель feedback и защиты эталонов не представлена | Использовать утверждённые Exercise/Evaluation/Feedback контракты, не копировать модель из прототипа |

## 4. Связь с S1–S9

| Навык | Что дают материалы | Что остаётся неподтверждённым |
|---|---|---|
| S1 | В HTML описаны только правила подсчёта граней и единиц | Полный ход партии, повышение ставок, Dudo, Palifico и переходы раундов |
| S2 | Визуальные экраны дают референсы отображения состояния и закрытой информации | Полнота DTO, защита скрытых значений, поведение при изменении состояния |
| S3 | HTML демонстрирует own matches и unknown dice | Все граничные случаи, активные/выбывшие игроки, Palifico и независимые эталоны |
| S4 | HTML демонстрирует биномиальную вероятность «не меньше» и таблицы | Точная дробная арифметика, событие «ровно», полный контракт Palifico и числовая верификация |
| S5 | Отдельные экраны визуально затрагивают механику ставок | Авторитетная таблица переходов и доказательство законности конкретных ставок |
| S6 | Один экран визуально показывает последовательность ставок | Событийная полнота, различие `BID_PLACED`/`TURN_ADVANCED`, неполные истории |
| S7 | Визуально присутствует оценка поведения/серии | Достаточность выборки, сопоставимость, факт/гипотеза, альтернативные объяснения |
| S8 | HTML содержит пороговое решение и максимальную заявку | Цель, полный набор доступных действий, оценка decision-time и допустимые альтернативы |
| S9 | Материалы не подтверждают полноценное планирование партии | Условные планы, триггеры пересмотра и долгосрочные ограничения |

## 5. Обязательные правила обращения с этими материалами

1. HTML и изображения остаются reference artifacts, а не authoritative ruleset.
2. Ни один порог прототипа не становится глобальным порогом продукта без отдельного решения владельца продукта.
3. Скриншот не подтверждает поведенческое требование; для него нужен тест или наблюдаемое свидетельство.
4. Пример из HTML нельзя считать `APPROVED` только потому, что он генерируется или визуально выглядит завершённым.
5. Любой перенос упражнения из прототипа требует нового `example_id`, версии ruleset/evaluator и заполненного review record.
6. Неизвестные режимы и правила блокируются, а не выводятся по аналогии.

## 6. Итог

Материалы полезны как ранние UX- и exercise-reference. HTML подтверждает узкий эксперимент с вероятностью и подсчётом, но выявляет различия с целевыми контрактами точной арифметики, независимого прогресса и явной оценки. Статичные экраны расширяют визуальный набор референсов, но не закрывают продуктовые и поведенческие критерии приёмки.

**Результат:** принять материалы как входные reference artifacts; не считать их доказательством готовности MVP и не переносить их пороги или правила в нормативные контракты без отдельного approval.
