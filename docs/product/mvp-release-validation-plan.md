# План финальной продуктовой приёмки MVP Perudo

**Статус:** план приёмки и передачи; не означает, что продукт уже прошёл тестирование.

## 1. Цель и границы

План определяет последовательность проверки продуктовой спецификации и будущего MVP. Он не выбирает стек, архитектурную технологию, базу данных или способ развёртывания. Проверяются продуктовые результаты и наблюдаемое поведение.

## 2. Последовательность release gates

| Gate | Область | Необходимые артефакты | Условие прохождения |
|---|---|---|---|
| G1 | Game Domain | Утверждённый ruleset, transition tables, Palifico edge cases | Все правила, используемые scored MVP, имеют статус APPROVED |
| G2 | Exercise catalogue | MVP scope, S1–S9 examples, review register | Каждый навык имеет хотя бы один APPROVED пример и семейство |
| G3 | Evaluation | Answer rubric, accepted alternatives, validation protocol | Для каждого примера определены обязательные критерии и тестовые ответы |
| G4 | Progress | Mastery/review policy, progress contract | Независимые попытки, hints, corrections и review сроки имеют утверждённую семантику |
| G5 | Recommendation | Learning Strategy policy | Приоритеты, learner override и no-eligible state согласованы |
| G6 | UX | UX acceptance, session scenarios | Пользователь понимает задачу, действие, результат и следующий шаг на desktop/mobile |
| G7 | End-to-end | X-E01–X-E04, recovery scenarios | Межмодульные границы, приватность и восстановление не нарушены |
| G8 | Handoff | Полный пакет, deferred list, sign-off | Нет открытых blocker для выбранного MVP scope; решения и версии зафиксированы |

Gates выполняются последовательно там, где нижестоящая проверка зависит от верхней. Например, scored-примеры не могут пройти G2 до закрытия необходимых правил G1.

## 3. Минимальный end-to-end набор

### E2E-01. Новичок завершает первое упражнение

Проверить: первый запуск, выбор навыка, краткую инструкцию, ответ, первичную обратную связь, полный разбор по запросу и следующий шаг.

**Pass:** пользователь может завершить одну попытку без необходимости читать всю справку; все submission events и progress facts сохранены согласно продуктовым контрактам.

### E2E-02. Ошибка и исправление

Проверить: неверную первую отправку, primary error, подсказку, исправление и итоговый результат.

**Pass:** первая ошибка не затирается; исправление не становится независимым mastery evidence; hint не превращается в штраф за корректность.

### E2E-03. Скрытая информация

Проверить S2 → S3 → S4 → S8.

**Pass:** закрытые значения не попадают в доступные пользователю данные; расчёт вероятности использует только корректные параметры; S8 оценивает выбор по информации decision-time.

### E2E-04. История и наблюдение

Проверить S6 → S7.

**Pass:** порядок событий точен; переход хода не считается ставкой; гипотезы не выдаются за факты; размер и сопоставимость выборки видны.

### E2E-05. Стратегия после изменения партии

Проверить S8 → S9 и изменение числа активных игроков.

**Pass:** единичное решение не оценивается по случайному исходу; план пересматривается при наблюдаемом изменении состояния; выбывший участник исключён из активного порядка, но сохраняется в истории.

### E2E-06. Возобновление сессии

Проверить закрытие/перезапуск приложения в состояниях незавершённой попытки, завершённой попытки и due review.

**Pass:** состояние восстанавливается без потери первой отправки, подсказок, исправлений и прогресса; пользователь не получает дублирующее независимое evidence из повторного открытия того же экземпляра.

## 4. Продуктовые негативные проверки

- Пример со статусом `DRAFT`, `READY_FOR_REVIEW`, `BLOCKED_BY_RULE_DECISION` или `RETIRED` не предлагается как scored exercise.
- Неизвестная версия ruleset/evaluator не приводит к молчаливой оценке по текущим правилам.
- Недостаточные данные не заменяются угадыванием.
- Неизвестное событие истории не интерпретируется как известная ставка.
- Повторный `command_id` с тем же payload не создаёт повторный эффект; тот же ID с другим payload даёт конфликт согласно reliability contract.
- Ошибка последнего snapshot не уничтожает возможность восстановления из предыдущего корректного snapshot, если это предусмотрено event-storage contract.
- Невалидный импорт резервной копии не должен частично перезаписывать локальный прогресс.
- Сброс прогресса требует явного подтверждения и не должен случайно происходить при изменении настроек упражнения.

## 5. Доказательства приёмки

Для каждого gate сохранять:

- идентификатор проверки;
- версию спецификации и ruleset;
- проверяемый сценарий/пример;
- ожидаемое наблюдаемое поведение;
- фактический результат;
- статус `PASS`, `FAIL`, `BLOCKED` или `N/A`;
- ссылку на дефект или решение;
- reviewer и дату.

Скриншот интерфейса сам по себе не доказывает корректность правил, приватности, восстановления или оценивания. Для таких требований требуется соответствующее поведенческое свидетельство.

## 6. Условия передачи команде реализации

Передавать MVP в реализацию можно, когда:

1. G1–G8 имеют статус PASS для согласованного scope;
2. все обязательные продуктовые решения приняты и перенесены в authoritative документы;
3. заблокированные и отложенные функции перечислены отдельно;
4. у каждого scored exercise есть APPROVED fixture и validation evidence;
5. UX-требования связаны с пользовательскими сценариями и проверяемыми результатами;
6. неизвестные и намеренно отложенные вопросы не замаскированы предположениями;
7. владелец продукта подписал пакет.

## 7. Форма итогового sign-off

| Область | Итог | Reviewer | Версия / ссылка | Дата |
|---|---|---|---|---|
| Game Domain / ruleset | OPEN | TBD | — | — |
| Exercise catalogue S1–S9 | OPEN | TBD | — | — |
| Evaluation | OPEN | TBD | — | — |
| Learning Progress | OPEN | TBD | — | — |
| Learning Strategy | OPEN | TBD | — | — |
| UX and accessibility | OPEN | TBD | — | — |
| End-to-end and recovery | OPEN | TBD | — | — |
| Product-owner approval | OPEN | TBD | — | — |

`OPEN` означает отсутствие подтверждённого результата, а не автоматический FAIL. До закрытия обязательных gates документ не должен называться доказательством готовности MVP.
