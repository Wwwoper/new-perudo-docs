# Perudo — надёжность межмодульных операций и идемпотентность

Версия: 1.0
Статус: проектный контракт надёжности.

## 1. Общие принципы

1. Сначала валидировать вход и полномочия, затем менять состояние.
2. Одна бизнес-операция не должна оставлять частично применённые данные.
3. Повтор технически доставленной операции не должен повторно учитывать бизнес-эффект.
4. Ошибки генерации, пользовательские ошибки и инфраструктурные ошибки различаются.
5. Восстановление использует сохранённые факты; оно не повторяет случайные операции.

## 2. Идентификаторы идемпотентности

### 2.1 Игровые команды

Каждая команда, меняющая GameState, имеет обязательный `command_id`.

- тот же `command_id` + тот же нормализованный payload → вернуть ранее сохранённый результат;
- тот же `command_id` + другой payload → `IdempotencyConflict`;
- новый ID → обычная валидация и выполнение.

`command_id` охватывает все операции изменения состояния, включая бросок, ставку, переход хода, Dudo и запуск следующего раунда.

### 2.2 Отправки ответов

Каждая отправка имеет устойчивый `submission_id` (или эквивалентный idempotency key).

Повтор идентичной отправки не создаёт вторую запись, не запускает повторное изменение счётчиков и не удваивает статистику. Разные отправки одного ответа пользователем могут быть отдельными событиями, если имеют разные IDs.

### 2.3 Обновление прогресса

Обновление прогресса должно быть идемпотентно относительно `submission_id`/attempt event ID. Повторная обработка результата Evaluation не увеличивает `submission_count`, `correction_count`, `hint_count` повторно.

Создание review task использует бизнес-ключ, исключающий дубликаты активных задач одного типа для того же навыка/периода.

## 3. Атомарные операции

| Операция | Атомарная логическая запись |
|---|---|
| Game command | Проверенный результат + все события команды + новое GameState |
| Dudo resolution | Вся последовательность DUDO/REVEAL/RESOLVE/LOSS/ELIMINATION/ROUND/GAME + новое состояние |
| Exercise creation | Валидированный immutable Exercise + Public/Private parts + generation metadata |
| Answer submission | AnswerSubmission + EvaluationResult + ссылка на evaluator/exercise versions |
| Attempt completion | Финальный статус + итоговые метрики попытки |
| Progress update | SkillProgress + history + error stats + review task changes |

Физическая транзакционная технология не определяется документом. Если операции позднее будут разделены между хранилищами, потребуется отдельный протокол согласованности; распределённая транзакция не предполагается для MVP.

## 4. Ошибки и повторные попытки

Категории:

- `DomainValidationError` — команда противоречит текущему состоянию/правилам; состояние не меняется.
- `GenerationError` — генератор не смог создать корректный вариант; это не ошибка ученика.
- `EvaluationInputError` — ответ имеет неверный формат/неполный payload; сохраняется согласно контракту отправок, но не подменяется корректным ответом.
- `NotFound` / `VersionUnavailable` — требуемый экземпляр или версия отсутствует; нельзя использовать latest version как незаметную замену.
- `IdempotencyConflict` — один ID использован для разных данных.
- `PersistenceError` — запись не подтверждена; вызывающая сторона не должна сообщать об успехе.
- `RecoveryError` — событие, snapshot или миграция не позволяют безопасно восстановить состояние.

Повторять можно только операции с известным безопасным поведением повторной доставки. Для игровых команд и AnswerSubmission сначала проверяется idempotency key.

## 5. Генерация упражнений

Порядок:

1. принять и нормализовать `ExerciseConfig`;
2. вызвать генератор с версионированной конфигурацией и `ExerciseRandomSource`;
3. проверить структурные и доменные инварианты;
4. проверить отсутствие утечки private data в public view;
5. сохранить полный экземпляр и метаданные;
6. только после подтверждения сохранения вернуть PublicExercise.

Если сохранение не подтверждено, экземпляр не показывается. Неуспешный кандидат не создаёт пользовательскую попытку.

Повтор генерации после сбоя может дать новый кандидат, если прежний экземпляр не был сохранён. Если сохранение могло пройти, но ответ потерян, операция должна быть разрешена по устойчивому operation ID, чтобы не создать второй экземпляр.

## 6. Проверка ответа

Evaluation всегда привязана к конкретным `exercise_id`, `exercise_version`, `evaluator_version` и сохранённым критериям.

Изменение evaluator не перепроверяет молча старые отправки. Повторная проверка старой отправки допустима только как отдельная явно версионированная операция с сохранением исходного результата.

Эталон не раскрывается до завершения упражнения. Исправления допускаются после обратной связи. Неограниченное количество отправок сохраняется как отдельные факты.

## 7. Восстановление Game Domain

Порядок:

1. загрузить snapshots в обратном порядке времени;
2. выбрать самый новый snapshot с поддерживаемой схемой и целостным содержимым;
3. если он повреждён, проверить предыдущий snapshot;
4. убедиться, что журнал после `last_event_sequence` непрерывен и все типы событий/версии payload известны;
5. применить события строго по sequence и ровно один раз;
6. проверить все доменные инварианты.

Если последний snapshot повреждён, fallback на предыдущий разрешён при полной целостности хвоста. Если все snapshots повреждены, но журнал целостен и мигрируем, допускается replay с начала. Неизвестный `event_type`, повреждённый журнал, неизвестная версия payload или отсутствующий мигратор — остановка с явной ошибкой.

Восстановление не вызывает `GameRandomSource`, не перебрасывает кубики и не выбирает первого игрока повторно.

## 8. Согласованность прогресса

Learning Progress обновляет агрегаты из сохранённых фактов попыток/отправок, а не из клиентских счётчиков.

Производные метрики могут быть пересчитаны из истории при наличии корректной версии алгоритма. Исходные отправки и результаты проверки не перезаписываются.

Сброс навыка создаёт новое состояние прогресса или событие сброса, сохраняя историю. Он не удаляет прошлые попытки.

## 9. Тесты надёжности

- Повтор команды с тем же ID/payload.
- Повтор команды с тем же ID и другим payload.
- Сбой между проверкой и сохранением.
- Сбой после commit, но до ответа вызывающей стороне.
- Повтор Dudo resolution.
- Повтор AnswerSubmission и обновления Progress.
- Дублирующая генерация после неопределённого результата сохранения.
- Повреждённый последний snapshot и fallback на предыдущий.
- Повреждение event tail, неизвестный event_type и отсутствие мигратора.
- Повторное восстановление не меняет случайные результаты и конечный GameState.
