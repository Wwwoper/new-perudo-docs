# Perudo — межмодульные границы и контракты

Версия: 1.2
Статус: проектный архитектурный контракт, основанный на согласованных контрактах Game Domain, S2–S4, Exercise, Evaluation и Learning Progress.

## 1. Назначение

Документ фиксирует ответственность модулей, направления зависимостей, публичные входы/выходы и запреты на передачу данных. Он не выбирает физическую структуру Python-пакетов, БД, ORM, веб-фреймворк или транспорт.

Архитектурная форма — модульный монолит. Вызовы между модулями в MVP — обычные синхронные вызовы прикладных сценариев/портов; доменные события сохраняются для истории и восстановления, но не требуют брокера или распределённой event-инфраструктуры.

## 2. Контекст модулей

| Модуль | Владеет | Не владеет |
|---|---|---|
| Game Domain | Правила, полное состояние партии, валидация команд, события и snapshots | UI, упражнения, прогресс обучения |
| S2 Perception | Представление стола для восприятия, задания на чтение состояния | Игровые правила, скрытые значения, расчёты S3/S4 |
| S3 Counting | Подсчёт совпадений и количества, `CountResult` | Вероятность, генерация состояния партии, выбор решения |
| S4 Probability | Точные вероятности и их учебная интерпретация | Подсчёт собственных кубиков, выбор ставки/действия |
| Exercise Engine | Генерация, валидация и сохранение экземпляров упражнений | Проверка ответов, прогресс навыков |
| Evaluation | Проверка отправки по критериям, partial credit, диагностика | Текст feedback, сохранение прогресса навыка |
| Feedback | Представление результата проверки понятным ученику | Изменение оценки, раскрытие запрещённых данных |
| Learning Progress | Факты попыток, метрики, состояние навыков, review tasks | Выбор следующего упражнения |
| Learning Strategy | Выбор навыка, типа/сложности и следующего упражнения | Хранение истины о попытках и статусах |
| Application | Сценарии пользователя и координация транзакционных границ | Повторная реализация доменных правил |
| Presentation | Отображение и сбор пользовательского ввода | Доступ к private data и самостоятельная оценка |

## 3. Направления зависимостей

Разрешённые направления:

- Application → порты модулей и сценарии;
- Exercise Engine → контракты навыков, Game Domain (только через генераторный адаптер/публичные фабрики ситуаций), S2/S3/S4 генераторы;
- S2 → read-only `PlayerGameView` / `ExerciseGameView` и адаптер представления;
- S3 → минимальный `CountContext` и правила подсчёта;
- S4 → `CountResult` и правила вероятности;
- Evaluation → сохранённый `PrivateExerciseData` и типизированный ответ;
- Feedback → `EvaluationResult` и разрешённый `PublicExercise`;
- Learning Progress → неизменяемые `ExerciseAttempt`, `AnswerSubmission`, `EvaluationResult`, hint events;
- Learning Strategy → read-модели Learning Progress и каталог навыков;
- Presentation → только публичные DTO/use-case results.

Запрещено:

- Presentation → GameState, PrivateExerciseData, ExpectedAnswer;
- S2 → S3/S4 с передачей закрытых значений чужих кубиков;
- S3 → S4 с повторной передачей исходных закрытых граней; передаётся `CountResult`;
- S4 → Game Domain с рекомендацией или командой ставки;
- Evaluation → Learning Strategy напрямую;
- Learning Progress → генератор для изменения уже сохранённого экземпляра;
- модулю-владельцу данных — читать/менять внутренние хранилища другого модуля в обход его порта.

## 4. Контракты между модулями

### 4.1 Game Domain → S2

Вход: `PlayerGameView` для реального режима или `ExerciseGameView` для упражнения, плюс layout-independent идентификаторы и разрешённые факты.

Адаптер преобразует доменные данные и при необходимости последовательность доменных событий в `TableView` / `TableTransition`.

S2 не интерпретирует правила событий. Он отображает уже вычисленное состояние. Событие `BID_PLACED` не должно само менять индикатор текущего игрока; смена игрока отражается только после `TURN_ADVANCED`.

### 4.2 Game Domain → S3

`CountContext` содержит:

- собственные значения кубиков;
- количество кубиков каждого участника, участвующего в расчёте;
- текущую ставку;
- `round_mode`;
- `ruleset_id` и `ruleset_version`.

Выбывшие игроки остаются в визуальном состоянии, но их кубики не входят в `total_dice_count` и `hidden_dice_count` текущего раунда.

`CountResult` содержит `own_matches`, `own_dice_count`, `total_dice_count`, `hidden_dice_count`, `required_matches`, `is_requirement_already_met`, `round_mode`, `ruleset_id`, `ruleset_version`.

S3 не получает и не сохраняет значения чужих закрытых кубиков.

### 4.3 S3 → S4

S4 получает `CountResult` и параметры события вероятности. S4 не пересчитывает `own_matches` и `required_matches`.

Для расчёта S4 использует `hidden_dice_count`, `required_matches`, `round_mode`, `ruleset_id/version`. Если `required_matches == 0`, вероятность выполнения требования равна 1. Если `required_matches > hidden_dice_count`, вероятность равна 0.

### 4.4 Game Domain → S4

Правила вероятности определяются режимом и версией правил:

| Режим | Грань ставки | p на скрытом кубике |
|---|---|---:|
| NORMAL | 2–6 | 1/3 |
| NORMAL | 1 | 1/6 |
| PALIFICO | 1–6 | 1/6 |

Вход S4 включает `round_mode`, `ruleset_id`, `ruleset_version`. Математическое ядро использует точные дроби.

### 4.5 Exercise Engine → Evaluation

Exercise Engine передаёт `exercise_id`, версию экземпляра, публичные вопросы, закрытый критерий проверки и ссылку на сохранённый `PrivateExerciseData`.

Evaluation не должен принимать эталон от клиента. Вызов проверки разрешается только по идентификатору сохранённого экземпляра и отправленному типизированному ответу.

### 4.6 Evaluation → Feedback → Learning Progress

Evaluation возвращает неизменяемый `EvaluationResult`: результаты полей/шагов, итог, partial credit, первичную и зависимые ошибки, диагностические ключи. Пользовательский `FeedbackView` формирует отдельный Feedback.

Feedback строит пользовательское сообщение, не меняя оценку и не раскрывая эталон до завершения упражнения.

Learning Progress получает отправку, результат проверки, использованные подсказки и версионные ссылки. Он обновляет попытку и агрегаты навыка в своей транзакционной границе.

### 4.7 Learning Progress → Learning Strategy

Learning Progress предоставляет read-модель состояния навыков, статистику ошибок и review tasks. Learning Strategy выбирает следующее упражнение, но не меняет историю попыток и не редактирует прогресс напрямую.

## 5. Владение данными

Каждый модуль является единственным владельцем своих записей и инвариантов. Другие модули используют его публичные команды/запросы или согласованные DTO.

Рекомендуемые логические владельцы:

- Game Domain: Game, GameState, DomainEvent, StateSnapshot;
- Exercise Engine: Exercise, PublicExercise, PrivateExerciseData, ExerciseConfig, generator metadata;
- Evaluation: вычисление `EvaluationResult`; не владеет `AnswerSubmission` и не хранит конкурирующую запись отправки;
- Learning Progress: `ExerciseAttempt` и вложенные `AnswerSubmission`, `EvaluationResult` как прикреплённый результат, SkillProgress, SkillProgressHistory, ErrorStatistics, ReviewSchedule, ReviewTask;
- Learning Strategy: постоянные правила подбора и конфигурация стратегии.

Физическое размещение таблиц/файлов может быть общим, но логическое владение не смешивается.

## 6. Общие правила версионирования

В каждом сохраняемом артефакте должны быть доступны релевантные версии:

- `ruleset_id` / `ruleset_version` — правила игры;
- `schema_version` — формат события, snapshot или контракта хранения;
- `generator_id` / `generator_version` — генерация упражнения;
- `exercise_version` — неизменяемая версия экземпляра;
- `evaluator_version` — алгоритм проверки;
- `feedback_version` — при необходимости воспроизводить текст/шаблон feedback.

Эти версии независимы. Изменение генератора не означает изменения правил, а изменение схемы хранения не означает изменение evaluator.

## 7. Транзакционные границы

- Изменение состояния партии: команда + события + новое состояние атомарны; `command_id` обязателен.
- Создание упражнения: generate → validate → persist выполняется до показа упражнения.
- Отправка ответа: `AnswerSubmission` сначала сохраняется со статусом `RECEIVED`; Evaluation выполняется отдельной восстанавливаемой стадией; результат прикрепляется со статусом `EVALUATED`; Progress обновляется отдельно и идемпотентно по `submission_id`.
- Обновление прогресса: попытка, метрики и переходы SkillProgress согласованно обновляются; повторная обработка одной отправки не удваивает метрики.
- Создание ReviewTask должно быть идемпотентным по типу/навыку/целевой дате или эквивалентному бизнес-ключу.

Точная реализация транзакций зависит от будущего хранилища и здесь не выбирается.

## 8. Наблюдаемость и безопасность

Ошибки межмодульного контракта должны содержать безопасный идентификатор операции и модуль-источник, но не закрытые значения кубиков и не эталон упражнения.

Логи не являются альтернативным хранилищем private data. В логах допустимы идентификаторы сущностей, версии и коды ошибок, но не закрытые игровые значения и ожидаемые ответы.

## 9. Что остаётся открытым

- Физическая структура Python-пакетов.
- Выбор БД, ORM и миграционного инструмента.
- Локальное/серверное исполнение и синхронизация.
- Точная схема хранения AnswerSubmission и EvaluationResult.
- Политика retention и экспорт/удаление пользовательских данных.
- Конкретные API DTO и сериализация.

Эти вопросы не меняют зафиксированные границы ответственности.


## 10. Принятые уточнения по генерации и типам упражнений

Skill-specific generators и evaluator adapters принадлежат соответствующим skill-модулям. Генератор создаёт типизированный candidate и private criteria; evaluator adapter выполняет предметно-специфичную проверку. Exercise Engine выбирает генератор, проверяет общий envelope, сохраняет immutable Exercise и разделяет public/private data. Общий Evaluation координирует evaluator adapters, зависимости, partial credit и общий `EvaluationResult`.

Все навыки используют единый верхнеуровневый Exercise envelope, но skill-specific payload остаётся типизированным (`skill_id + exercise_type`). Универсальный неструктурированный payload и отдельные хранилища упражнений в skill-модулях не допускаются. Вопросы могут иметь разные типы взаимодействия; идентификаторы зон/областей стола должны быть независимы от экранной позиции. Многошаговые упражнения описываются упорядоченными шагами с явными зависимостями и required/optional.

## 11. Канонический вход S3

Игровой `CountContext` содержит только активных участников. Общее количество кубиков вычисляется из количества кубиков этих участников; выбывшие остаются только в визуальных read models. Диагностические упражнения, которым требуется показать некорректный список участников, используют отдельный типизированный вход и не меняют семантику игрового `CountContext`.

## 12. Генерация и старт попытки

Exercise сохраняется до показа. Создание попытки — отдельный явный use case `StartExerciseAttempt`, выполняемый при начале прохождения. Предварительная генерация/загрузка не создаёт попытку. Повтор `operation_id` с тем же payload возвращает исходную сущность; с другим payload — `IDEMPOTENCY_CONFLICT`.

## 13. Версионирование

Версии схемы persisted artifacts независимы от версий ruleset, generator и evaluator. Внутренние DTO модульного монолита не получают версию автоматически; их совместимость проверяется контрактными и интеграционными тестами. Внешнее versioned API не входит в первый релиз.
