# Perudo — архитектура web-клиента MVP

Версия: 1.0
Статус: целевая логическая архитектура web-first MVP; конкретный frontend framework и инструменты сборки не выбраны.

## 1. Назначение

Документ переводит принятое решение о responsive web-платформе в логические границы runtime. Он не выбирает frontend framework, CSS toolkit, bundler, ORM или физическую структуру Python-пакетов.

## 2. Runtime и deployment

MVP — browser-only application с локальным исполнением доменных и прикладных сценариев.

- Статический hosting доставляет версионированные ресурсы приложения по HTTPS.
- После загрузки приложение выполняет игровые и учебные use cases в браузере.
- Сервер не принимает пользовательские ответы, не хранит профиль и не проверяет упражнения.
- Service Worker/PWA cache отвечает только за доставку app shell и статических ресурсов; это не источник истины пользовательских данных.
- Обновление ресурсов приложения не должно очищать или перезаписывать пользовательское хранилище.

## 3. Логические слои

| Слой | Ответственность | Запреты |
|---|---|---|
| Presentation | Responsive UI, доступность, ввод, отображение публичных view models | Не содержит доменных правил и не читает private storage напрямую |
| Application | Use cases, координация модулей, обработка ошибок и транзакционных границ | Не дублирует игровые правила и evaluator |
| Domain modules | Game Domain, Skills, Exercise Engine, Evaluation, Feedback, Learning Progress, Learning Strategy | Не зависят от browser APIs и UI |
| Ports | Типизированные интерфейсы репозиториев, clock/id generation и файлового export/import | Не раскрывают детали конкретного browser storage |
| Browser infrastructure adapters | IndexedDB adapter, backup file adapter, app cache adapter | Не содержат предметной логики |

Существующие границы модулей и владельцы данных из `module-boundaries.md` сохраняются. Новый слой не создаёт альтернативного владельца `Exercise`, `AnswerSubmission`, `Game` или `SkillProgress`.

## 4. Локальное хранение

Для MVP рекомендуется IndexedDB как browser-native persistent storage:

- сохраняемые агрегаты и события принадлежат своим доменным модулям;
- доступ к IndexedDB инкапсулирован адаптерами репозиториев;
- транзакции IndexedDB используются для атомарного сохранения в пределах одной логической операции;
- операции, которые по архитектуре состоят из нескольких стадий, сохраняют checkpoint/status и восстанавливаются идемпотентно;
- крупные или бинарные backup-файлы не хранятся как единственный экземпляр внутри IndexedDB;
- `localStorage` не используется для критичных игровых/учебных записей; допустим только для некритичных UI preferences при необходимости.

IndexedDB — принятое направление для MVP, но конкретная схема object stores, индексы и библиотека-обёртка определяются при проектировании persistence adapter.

## 5. Offline-поведение

Основные локальные сценарии PS-01–PS-09 должны работать без сетевых запросов после успешной загрузки приложения и необходимых ресурсов.

- App shell и необходимые статические ресурсы кэшируются версионированно.
- Учебные упражнения генерируются локально по существующим контрактам.
- Проверка и обновление прогресса выполняются локально.
- Партии и учебный прогресс читаются из IndexedDB.
- Ошибка обновления/проверки service worker не должна удалять старый рабочий app shell.
- Если storage недоступен или quota исчерпана, приложение не должно показывать ложное подтверждение сохранения.
- Внешние шрифты, CDN и сторонние API не должны быть обязательны для основного offline-сценария.

## 6. Trust model и private data

Режим проверки — `TRUSTED_LOCAL`.

Это означает:

- пользователь может исследовать клиентский runtime, локальное хранилище, bundle и сетевые ресурсы;
- `PrivateExerciseData` и expected answers могут быть извлечены владельцем устройства;
- local validation защищает от случайной ошибки и поддерживает корректный учебный flow, но не является anti-cheat механизмом;
- разделение `PublicExercise` и `PrivateExerciseData` сохраняется как архитектурный контракт и не позволяет случайно передавать private поля в Presentation DTO;
- закрытые грани соперников не должны попадать в публичные view models, UI state, логи или экспортируемые диагностические события до разрешённого раскрытия;
- нельзя обещать защиту от модификации локального прогресса или результатов партии владельцем устройства.

Если в будущем потребуется доверенная проверка, понадобится серверная граница: серверный источник эталона, аутентификация/идентификация сессии, защита от повторной отправки и пересмотр публичных DTO. Это отдельный ADR, не скрытая возможность текущей схемы.

## 7. Сохранение и восстановление

- UI показывает подтверждение сохранения только после успешного завершения операции persistence adapter.
- При ошибке записи операция возвращает типизированную ошибку и сохраняет возможность безопасного повтора.
- `operation_id`, `command_id` и `submission_id` сохраняют согласованную семантику идемпотентности.
- После reload приложение восстанавливает незавершённые операции по lifecycle state machines.
- Обновление приложения не меняет persisted data напрямую; миграции запускаются явным версионированным шагом.
- Повреждённое или неизвестное состояние не сбрасывается автоматически.

## 8. Адаптивный интерфейс

- Один продуктовый сценарий и один набор use cases для desktop и mobile.
- Responsive layout меняет расположение, плотность и способ ввода, но не меняет смысловую модель и идентификаторы.
- На desktop поддерживаются мышь и клавиатура; на mobile — touch и системная клавиатура.
- Основная задача и главное действие остаются визуально приоритетными.
- На узком экране длинная справка сворачивается/открывается по запросу, но не скрывает обязательные данные задачи.
- Проверки WCAG 2.2 AA применяются к web UI.

## 9. Проверки и тестовые уровни

1. Domain unit tests запускаются без browser runtime.
2. Adapter contract tests проверяют IndexedDB adapter на соответствие портам репозиториев.
3. Persistence integration tests проверяют атомарность, повтор операции, quota/storage errors и восстановление после reload.
4. Offline tests проверяют холодный запуск после предварительного cache и сценарий обновления service worker.
5. Browser E2E tests покрывают PS-01–PS-09 в desktop и mobile viewport.
6. Security tests проверяют отсутствие private data в публичных DTO, DOM-visible state, логах и диагностике; отдельно фиксируется, что извлечение из local runtime возможно и не считается дефектом `TRUSTED_LOCAL`.
7. Accessibility tests проверяют клавиатуру, focus order, screen-reader semantics, zoom и touch target.

## 10. Ограничения

Browser storage может быть очищено пользователем, браузером, политиками приватности или системой при нехватке места. Приложение не может гарантировать сохранность локального профиля при потере/сбросе устройства или browser profile. Поэтому ручной backup и проверяемое восстановление — обязательная часть готовности к публичному релизу.
