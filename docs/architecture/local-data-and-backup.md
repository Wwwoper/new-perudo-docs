# Perudo — локальные данные, backup и восстановление

Версия: 1.0
Статус: принятое направление MVP; точная бинарная/JSON-схема backup уточняется в persistence design.

## 1. Цели и ограничения

MVP хранит один профиль локально в browser storage одного устройства. Облачной синхронизации и серверной копии нет.

Цели:

- сохранять подтверждённые партии, упражнения, попытки, отправки, результаты и прогресс между запусками;
- явно сообщать о невозможности сохранения;
- позволять пользователю экспортировать backup и восстановить его на другом устройстве/в другом браузере;
- обнаруживать повреждение, неподдерживаемую версию и неполный backup до изменения текущего профиля.

Не обещается автоматическое восстановление после потери устройства или очистки browser storage без заранее созданной пользователем копии.

## 2. Классы данных

| Данные | Политика MVP |
|---|---|
| Game, события и snapshots | Локально сохраняются; входят в backup |
| Exercise и private criteria | Локально сохраняются для воспроизводимой проверки; входят в backup, поскольку backup принадлежит пользователю и trust model — TRUSTED_LOCAL |
| ExerciseAttempt, AnswerSubmission, EvaluationResult | Сохраняются по lifecycle/идемпотентным контрактам; входят в backup |
| SkillProgress, history, review tasks | Сохраняются; входят в backup |
| UI preferences | Некритичные; могут быть включены, если это не усложняет совместимость |
| Runtime cache и service worker cache | Не являются пользовательскими данными; не входят в backup |
| Диагностические логи | Не являются источником истины; не входят в обычный backup |

Не собирать имя, email или иные идентификаторы пользователя в MVP без отдельной продуктовой необходимости.

## 3. Политика записи

- Успешный ответ UI о сохранении выдаётся только после завершения устойчивой записи.
- Для команды/операции повтор с тем же ID и payload не создаёт дубликат; тот же ID с другим payload возвращает конфликт согласно существующим контрактам.
- Состояния многошаговой операции сохраняются так, чтобы приложение могло продолжить или безопасно повторить незавершённую стадию.
- Сохранение события и соответствующего нового GameState атомарно.
- Ошибки quota, storage unavailable и transaction abort показываются явно; приложение не продолжает сценарий так, будто данные сохранены.

## 4. Формат backup

Для MVP рекомендуется один переносимый файл backup с:

- `backup_format_id` и `backup_format_version`;
- `created_at` в UTC;
- версией приложения/экспортёра;
- списком persisted artifact schema versions;
- полным набором данных профиля, необходимым для восстановления;
- контрольной суммой содержимого для обнаружения случайного повреждения.

Формат должен быть документирован, детерминированно сериализуем и не зависеть от внутреннего устройства IndexedDB. Конкретный формат файла и алгоритм checksum фиксируются отдельной спецификацией до реализации export/import.

Backup не является зашифрованным хранилищем. В нём могут находиться история партий и учебные эталоны. UI предупреждает пользователя хранить файл в безопасном месте и не отправлять его третьим лицам без необходимости. Шифрование backup не входит в обязательный MVP; если будет добавлено, потребуется отдельный UX для пароля, восстановления и потери ключа.

## 5. Экспорт

- Экспорт запускается пользователем явно из настроек/раздела данных.
- До создания файла приложение проверяет согласованность экспортируемого набора.
- Экспорт не удаляет и не изменяет исходный профиль.
- Пользователь получает файл только после успешной сериализации и проверки checksum.
- Ошибка экспорта не должна приводить к частичному удалению или изменению локальных данных.

## 6. Импорт и восстановление

Импорт — явная операция, не фоновая синхронизация.

Порядок:

1. Прочитать файл в изолированную staging-область, не меняя текущий профиль.
2. Проверить формат, checksum, обязательные поля, schema versions и допустимость миграций.
3. Показать пользователю сводку: профиль/набор данных, дата backup, версии, число партий и учебных записей; не раскрывать лишние private details.
4. Предупредить, что восстановление заменит текущий локальный профиль.
5. Предложить экспортировать текущий профиль перед заменой.
6. После явного подтверждения атомарно заменить профиль либо выполнить транзакционную публикацию подготовленного набора.
7. Проверить читаемость восстановленных агрегатов и показать результат.

В MVP выбран режим **полного восстановления с заменой текущего профиля**. Автоматическое объединение двух профилей не выполняется: merge требует отдельной семантики конфликтов для партий, попыток и идентификаторов.

Если файл повреждён, версия не поддерживается или миграция невозможна, импорт завершается без изменения текущего профиля.

## 7. Версионирование и миграции

- `backup_format_version` не заменяет версии отдельных persisted artifacts.
- `schema_version`, `ruleset_version`, `generator_version` и `evaluator_version` остаются независимыми.
- Миграции явные, последовательные и покрыты fixtures предыдущих версий.
- Неизвестная будущая версия не интерпретируется как текущая.
- Миграция выполняется в staging; оригинальный backup не перезаписывается.
- Если старый evaluator/ruleset недоступен, данные сохраняются, но приложение явно обозначает, что повторная проверка/воспроизведение конкретной записи недоступны.

## 8. Удаление и сброс

Различать три действия:

1. **Сброс прогресса навыка** — сохраняет историю, как определено Learning Progress.
2. **Сброс локального профиля** — отдельное явное действие с предупреждением и подтверждением; до выполнения рекомендуется экспорт.
3. **Очистка browser storage/удаление приложения** — может удалить данные вне контроля приложения; перед удалением PWA/данных браузер должен показывать понятное предупреждение, если платформа предоставляет такую возможность.

Политика retention для MVP: данные хранятся до явного сброса/удаления пользователем или очистки browser storage; автоматическое удаление истории по сроку не выполняется.

## 9. Восстановительные тесты

Обязательные сценарии:

- export → очистка тестового хранилища → import → проверка количества и целостности агрегатов;
- import поверх непустого профиля с отменой — исходные данные не изменились;
- import поверх непустого профиля с подтверждением — текущий профиль заменён целиком;
- повреждённый checksum — отказ без изменения профиля;
- неизвестная версия backup/schema — отказ без изменения профиля;
- ошибка quota/transaction во время restore — профиль остаётся в согласованном старом состоянии;
- миграция каждой поддерживаемой предыдущей версии на fixtures;
- повторное восстановление одного backup не создаёт объединённых дубликатов, поскольку операция заменяет профиль.

## 10. Критерий готовности к публичному релизу

Публичный релиз не готов без пользовательского export/import flow, проверяемой checksum, теста полного восстановления и понятного предупреждения о риске потери browser storage. Сам факт успешного скачивания backup-файла недостаточен — должен быть проверен обратный путь восстановления.
