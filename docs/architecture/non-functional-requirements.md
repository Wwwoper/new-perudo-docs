# Perudo — нефункциональные требования первого релиза

Версия: 1.1
Статус: базовый набор требований и критериев проверки для принятого browser-only web MVP. Числовые пороги ниже — проектные цели, а не измеренные характеристики текущей реализации.

## 1. Область

Требования относятся к адаптивному web-приложению для desktop/mobile с browser-only исполнением учебного ядра и локальной партии Perudo. Статический hosting доставляет ресурсы приложения, но пользовательский backend, облачная синхронизация и сетевой multiplayer не входят в базовый профиль MVP. См. `platform-and-distribution.md` и `web-client-architecture.md`.

## 2. Производительность

Целевые значения на согласованном референсном устройстве/среде после выбора платформы:

| Операция | Цель MVP |
|---|---:|
| Открытие главного/учебного экрана из локальных данных | p95 <= 500 мс |
| Выдача уже сохранённого PublicExercise | p95 <= 200 мс |
| Генерация и сохранение стандартного упражнения | p95 <= 1 с; сложные сценарии отдельно измерить |
| S3/S4 точные расчёты для допустимых размеров стола | p95 <= 100 мс |
| Evaluation одного ответа | p95 <= 200 мс |
| Локальное сохранение отправки/события | p95 <= 200 мс |

Измерять отдельно cold start, warm path и операции с диском. Не оптимизировать до появления профиля; сначала обеспечить корректность и воспроизводимые benchmark fixtures.

## 3. Надёжность и целостность

Обязательные требования:

- подтверждённое сохранение не теряется при штатном закрытии приложения;
- все изменяющие операции имеют устойчивый operation/command/submission ID;
- повтор операции не создаёт дубликат и не применяет метрики повторно;
- Exercise immutable после сохранения;
- отправки, результаты проверки и обновление прогресса восстанавливаются по стадиям;
- доменные события и соответствующее состояние сохраняются атомарно;
- Dudo применяется атомарно;
- повреждённые/неизвестные данные приводят к явной ошибке, а не к молчаливой потере;
- миграции форматов явные, версионированные и тестируемые.

Цели восстановления:

- RPO для подтверждённых локальных операций: 0 при штатной работе и корректном закрытии; поведение при физической потере/повреждении устройства не гарантируется без backup;
- RTO после обычного перезапуска: приложение открывает последнее подтверждённое состояние без ручного восстановления; целевой p95 до 3 секунд на референсном объёме данных.

## 4. Хранение, резервирование и восстановление

Рекомендация MVP:

- сохранять локальные учебные записи и партии между запусками;
- не обещать облачный backup до выбора платформы и механизма синхронизации;
- предоставить понятный сценарий ручного экспорта резервной копии до внедрения облачной синхронизации;
- экспорт должен включать schema/version metadata и проверку целостности;
- импорт не должен незаметно перезаписывать существующий профиль; требуется предварительный просмотр/подтверждение и стратегия конфликта;
- резервная копия должна быть проверяема тестом восстановления, а не только фактом успешного создания файла.

Срок хранения, полное удаление и экспорт пользовательских данных должны быть утверждены до публичного релиза, если приложение хранит персональные/идентифицирующие данные или распространяется как облачный сервис.

## 5. Безопасность и приватность

Обязательные инварианты:

- закрытые грани соперников не попадают в PlayerGameView/TableView/логи до разрешённого раскрытия;
- expected answers/private criteria не попадают в PublicExercise или клиентские логи;
- локальный TRUSTED_LOCAL не рекламируется как защита от владельца устройства;
- данные профиля минимальны; в рекомендуемом MVP не требуется имя/email;
- диагностические логи используют IDs, версии и безопасные коды, не private payload;
- сброс прогресса не удаляет историю; полное удаление профиля — отдельная операция с явной политикой;
- сторонняя телеметрия/аналитика не включается без обоснованной цели и прозрачного уведомления.

Перед выпуском провести threat review минимум для: локального извлечения эталона, подмены локальных данных, повторной отправки, порчи файла сохранения, доступа другого локального пользователя к профилю и утечки через диагностические логи.

## 6. Доступность и UX

Цели:

- основные сценарии доступны с клавиатуры/эквивалентных средств ввода выбранной платформы;
- фокус видим и следует логическому порядку;
- текстовые статусы и ошибки не кодируются только цветом;
- масштабирование текста не обрезает основные действия и данные задачи;
- контраст, размеры интерактивных целей и семантика элементов проверяются по актуальному стандарту доступности для выбранной платформы; целевой ориентир — WCAG 2.2 AA для web-поверхностей;
- при ошибке формы пользователь видит, какое поле требует исправления, и введённые корректные значения не теряются.

UX-цели по аудиту:

- один главный вопрос/действие на экране;
- короткая инструкция, подробная справка по запросу;
- вывод решения до математических деталей;
- единый порядок смысловых зон во всех упражнениях;
- чёткое разделение текущей ставки и истории ставок.

## 7. Совместимость и миграции

- persisted contracts (events, snapshots, exercises, submissions, evaluation records) имеют независимые версии;
- неизвестная версия не интерпретируется как текущая;
- мигратор имеет unit tests и fixtures предыдущих версий;
- старые упражнения проверяются по сохранённым версиям evaluator/ruleset либо возвращают VERSION_UNAVAILABLE;
- внутренние DTO не версионируются автоматически без реальной потребности;
- обновление приложения не должно молча сбрасывать историю или прогресс.

## 8. Наблюдаемость и диагностика

Минимально допустимая диагностика:

- operation_id/correlation_id, entity IDs, версия схемы/правил/генератора/evaluator;
- длительность генерации, сохранения, оценки, восстановления;
- безопасный error code и retryability;
- диагностические события не содержат private dice values, expected answers или полный профиль.

В MVP достаточно структурированных локальных логов и диагностического отчёта, который пользователь может явно приложить к обращению. Автоматическая отправка логов не включается по умолчанию.

## 9. Тестируемость и качество

Обязательные уровни:

1. Unit tests: правила Game Domain, S2/S3/S4 математика, evaluator, переходы состояний, адаптация прогресса.
2. Property-based или exhaustive tests там, где пространство входов мало и это полезно: вероятности биномиального распределения, границы количества кубиков, очередность игроков.
3. Contract tests: public/private DTO, module ports, version compatibility.
4. Integration tests: сквозные сценарии PS-01–PS-09, сбои между стадиями, повтор команд.
5. Recovery tests: восстановление после перезапуска, fallback snapshot, импорт backup.
6. UX/accessibility checks: keyboard/focus, масштабирование, контраст, ясность ошибок.

Сборка релиза не должна проходить при нарушении обязательных инвариантов приватности, идемпотентности или целостности.

## 10. Browser-specific requirements

- Основные сценарии PS-01–PS-09 работают в поддерживаемых desktop/mobile browsers.
- После первого успешного открытия app shell и необходимые ресурсы доступны offline через versioned cache.
- Service Worker cache не является источником истины пользовательских данных и не очищает IndexedDB при обновлении.
- Ошибки browser storage, quota и transaction abort явно показываются; UI не сообщает об успешном сохранении до commit.
- Browser storage может быть очищено пользователем/браузером/ОС; пользователь предупреждается о необходимости backup.
- Основные сценарии не зависят от hover, внешних CDN и обязательных сетевых API.

## 11. Что измерить до финального утверждения

Пока не выбраны платформа, референсное устройство, размер ожидаемой истории и способ хранения, performance/RTO цифры являются целями, а не SLA. После фиксации browser/OS/device support matrix нужно определить benchmark environment и проверить значения на реальных сценариях.
