# Perudo — проверка готовности продуктовой архитектуры

Версия: 1.1
Статус: аудит покрытия пользовательских сценариев и открытых продуктовых решений.

## 1. Результат

Логические границы модулей и ADR-001–ADR-012 закрыты. Пользовательские сценарии, lifecycle, нефункциональные требования и целевая web-платформа зафиксированы. `platform-and-distribution.md`, `web-client-architecture.md` и `local-data-and-backup.md` уточняют runtime, локальное хранение и восстановление, не выбирая frontend framework или физическую структуру Python-пакетов.

## 3. Принятые решения для MVP

1. Один локальный профиль без обязательной регистрации.
2. Адаптивное web-приложение для desktop и mobile; PWA-installability — progressive enhancement.
3. Один пользователь на одном устройстве/browser profile; без облачной синхронизации.
4. Без сетевого multiplayer и социальных функций.
5. Локальная проверка в `TRUSTED_LOCAL` с честным описанием границ доверия.
6. Локальное устойчивое хранение подтверждённых партий и учебных фактов через browser storage adapter; для MVP рекомендуется IndexedDB.
7. Ручной export/import backup до публичного релиза; восстановление полностью заменяет профиль после preview и подтверждения.
8. Прозрачные правила Learning Strategy, без ML.
9. Единая структура учебных экранов с одним главным действием.
10. Browser-only runtime без обязательного пользовательского backend; статический hosting доставляет ресурсы приложения.

## 4. Решения, которые остаются открытыми

Следующие решения не блокируют платформенный MVP и могут быть приняты на этапе реализации:

- конкретный frontend framework, bundler и CSS/UI toolkit;
- физическая структура Python-пакетов и способ размещения/исполнения Python-кода, если он потребуется;
- точная схема IndexedDB stores, индексы и библиотека-обёртка;
- точный сериализованный формат backup и checksum algorithm;
- референсные browser/OS/device matrix и benchmark environment;
- окончательная политика privacy notice и формулировки пользовательских предупреждений;
- требования к поддержке несовершеннолетних, если продуктовая аудитория будет включать эту группу.

Принятый browser-only runtime не предоставляет серверной авторитетности. Любой переход к backend, аккаунтам или синхронизации требует отдельного пересмотра trust model, privacy и API contracts.

## 5. Критерий перехода к проектированию Python-пакетов

Можно переходить к проектированию физической структуры модулей и persistence adapter, когда:

- продуктовые сценарии PS-01–PS-09 приняты как MVP scope;
- выбрана целевая платформа и модель распространения;
- утверждено направление browser storage и определены backup, export, import и delete политики;
- performance targets привязаны к референсной среде;
- security/privacy threat review не выявил неразрешённых критических рисков;
- межмодульные контракты не имеют противоречащих друг другу владельцев данных.

До этого момента допустимо уточнять логические интерфейсы и тестовые сценарии, но не следует фиксировать пути Python-импортов или выбирать конкретные технологии хранения.
