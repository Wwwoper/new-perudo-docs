# Perudo — реестр открытых архитектурных решений

Версия: 1.0
Статус: решения, требующие подтверждения перед проектированием Python-пакетов.

Документ не отменяет ранее согласованные контракты. Варианты ниже являются рекомендациями для принятия решения.

## ADR-001. Владелец AnswerSubmission

**Рекомендация:** Learning Progress владеет отправкой как фактом действия пользователя и её связью с `ExerciseAttempt`; Evaluation вычисляет результат без собственного конкурирующего хранилища отправок.

**Почему:** одна отправка должна иметь один идентификатор, одну историю и один источник истины для метрик.

**Альтернатива:** Evaluation владеет отправками и отдаёт Learning Progress ссылку/событие. Тогда необходимо формально перенести владение из текущего контракта Learning Progress и описать согласованность двух модулей.

## ADR-002. Владелец завершения попытки

**Рекомендация:** Learning Progress владеет статусом попытки; Application координирует завершение; Exercise Engine владеет completion criteria и выдаёт review view только после подтверждённого завершения.

**Нужно подтвердить:** можно ли завершить упражнение досрочно, если обязательные шаги выполнены, но необязательные остались незаполненными. Текущий контракт говорит, что optional steps не влияют на обязательный балл, но не задаёт все условия завершения.

## ADR-003. Skill-specific генераторы

**Рекомендация:** генератор S2/S3/S4 формирует candidate и private criteria; Exercise Engine регистрирует/вызывает генератор, проверяет общий envelope, сохраняет экземпляр и формирует PublicExercise.

**Нужно подтвердить:** генератор является частью skill-модуля или отдельным адаптером Exercise Engine. Рекомендуется первый вариант по владению предметными правилами.

## ADR-004. BID_PLACED → TURN_ADVANCED

**Вариант A — рекомендуемый для MVP:** две команды и два события остаются отдельными; Application выполняет `PlaceBidAndAdvanceTurn` и надёжно повторяет `AdvanceTurn` после неопределённого результата по сохранённому operation state. Домен допускает кратковременное состояние «ставка принята, переход хода ожидает завершения».

**Вариант B:** одна внешняя команда атомарно создаёт два доменных события в одной транзакции. Тогда нужно определить, сохраняется ли семантическая отдельность команд и что именно означает `command_id`.

**Нужно подтвердить:** допустимо ли промежуточное состояние между двумя событиями или операция должна быть атомарной целиком.

## ADR-005. Доверенная среда Evaluation

**Рекомендация:** сохранить два профиля исполнения:

- `TRUSTED_LOCAL` — эталон доступен локальному процессу приложения; не обещается защита от пользователя, контролирующего устройство;
- `TRUSTED_SERVER` — эталон и проверка находятся на сервере; клиент получает только public view и результат.

**Нужно подтвердить:** первый релиз является локальным приложением с честным предупреждением о границе доверия или сразу требует серверной проверки.

## ADR-006. Сбой между сохранением отправки и обновлением Progress

**Рекомендация:** отправка сохраняется с `submission_id` до проверки; Evaluation выполняется по сохранённому упражнению и версии; результат прикрепляется идемпотентно; Progress применяет его по тому же `submission_id`. Повторный вызов продолжает незавершённый шаг.

**Нужно подтвердить:** в MVP допускается ли одна логическая транзакция Application для отправки, оценки и Progress, или сохраняем отдельные восстанавливаемые стадии. Рекомендация — отдельные стадии с идемпотентностью, чтобы не зависеть от длительности/сложности Evaluation.

## ADR-007. Модель CountContext

**Рекомендация:** передавать только активных участников и собственные значения; `total_dice_count` вычислять из переданных количеств, не принимать независимо. Выбывшие остаются только в TableView.

**Нужно подтвердить:** требуется ли S3 полный список участников с `is_active` для специальных упражнений на обнаружение ошибки. Если да, такой формат должен быть отдельным входом для учебного задания, а не обычным игровым `CountContext`.

## ADR-008. Создание ExerciseAttempt

**Рекомендация:** создавать попытку при явном старте упражнения до первого ответа. Открытие экрана с тем же `attempt_id` не создаёт новую попытку; новое прохождение получает новый `attempt_id` и новый экземпляр упражнения.

**Нужно подтвердить:** создаём ли попытку автоматически при выдаче упражнения или отдельным действием «Начать». Рекомендация — отдельный start use case, чтобы не считать предварительно загруженное/неоткрытое задание попыткой.

## ADR-009. Владение FeedbackResult

**Рекомендация:** `EvaluationResult` хранит только диагностические ключи и структуру оценки; `FeedbackView` принадлежит Feedback и зависит от `feedback_version`.

**Нужно подтвердить:** нужна ли точная воспроизводимость текста feedback для старых попыток или достаточно сохранять код/версию шаблона и при просмотре формировать текст заново.

## ADR-010. Идемпотентность генерации

**Рекомендация:** `CreateExercise` принимает устойчивый `operation_id`; при повторе с тем же payload возвращает тот же `exercise_id`, при другом payload — конфликт. Это закрывает сбой после commit, но до ответа клиенту.

**Нужно подтвердить:** сохранять ли незавершённую попытку только после отдельного `StartExerciseAttempt`, как рекомендовано в ADR-008.

## ADR-011. Граница между S2 и Exercise Engine

**Рекомендация:** S2 определяет perception task schema, генератор S2 формирует специфичное содержимое, Exercise Engine управляет жизненным циклом экземпляра. Не создавать отдельное хранилище упражнений внутри S2.

**Нужно подтвердить:** принять ли единый Exercise envelope для всех навыков S1–S9, включая вопросы с кликом по области стола и многошаговые упражнения.

## ADR-012. Версии DTO и совместимость

**Рекомендация:** версионировать сохраняемые артефакты (events, snapshots, exercises, submissions/evaluation records) и отдельно версионировать внешние DTO только при необходимости совместимости нескольких клиентов. Не добавлять `schema_version` в каждый внутренний вызов автоматически.

**Нужно подтвердить:** нужен ли внешний API/несколько клиентов в первом релизе. Если нет, начать с версионирования persisted contracts и явной совместимости внутренних DTO через тесты.

## Порядок принятия

Блокирующие до физического проектирования:

1. ADR-001 и ADR-002 — владение учебными записями и завершением;
2. ADR-004 — переход хода;
3. ADR-005 и ADR-006 — доверие и надёжность проверки;
4. ADR-003 и ADR-011 — граница генераторов;
5. ADR-007…ADR-012 — уточнение интерфейсов и версионирования.
