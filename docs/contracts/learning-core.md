# Учебное ядро — Exercise, Evaluation и Learning Progress

Версия: 1.0
Статус: согласованные межмодульные контракты.

## 1. Exercise Contract

### 1.1 Назначение

Exercise Engine создаёт, валидирует и сохраняет конкретные экземпляры упражнений. Он не проверяет правильность ответа и не определяет прогресс навыка.

### 1.2 Модели

- `Exercise` — метаданные и жизненный цикл экземпляра;
- `PublicExercise` — разрешённое клиенту условие;
- `PrivateExerciseData` — эталон и закрытый контекст;
- `Question` — вопрос/шаг внутри упражнения;
- `ExpectedAnswer` и `ExpectedFields` — закрытые ожидаемые значения;
- `EvaluationCriteria` — правила оценки;
- `DiagnosticContext` — контекст для диагностики;
- `ExerciseConfig` — параметры генерации;
- `ExerciseGenerator` — контракт генератора.

Публичная и закрытая части строго разделены. Эталон не передаётся в UI, сериализуемые публичные ответы, клиентские логи или диагностические сообщения.

### 1.3 Генерация и сохранение

Каждый экземпляр сохраняется сразу после успешной генерации и валидации. Одного seed недостаточно: сохраняется сам экземпляр, seed, идентификатор и версия генератора, конфигурация и ruleset id/version.

Один экземпляр может содержать несколько вопросов и последовательных шагов. Каждый шаг может быть обязательным или необязательным.

Повторение создаёт новый вариант того же типа и сложности, а не повторяет исходный экземпляр.

Ошибки генерации отделены от ошибок ученика.

### 1.4 Жизненный цикл

`config → generate → validate → persist → public view → answer → evaluation`.

Проверка на первом этапе может выполняться локально. Контракт допускает перенос проверки на сервер без изменения публичной модели упражнения.

## 2. Evaluation Contract

### 2.1 Назначение

Evaluation проверяет формат, значения полей, шаги и упражнение в целом. Он возвращает структурированный результат и не формирует пользовательский текст обратной связи.

### 2.2 Модели

- `AnswerSubmission` — одна отправка;
- `SubmittedAnswer` — типизированный ответ;
- `AnswerFormat` — ожидаемый формат;
- `EvaluationResult` — итог проверки;
- `FieldResult` — результат поля;
- `StepResult` — результат шага;
- `DiagnosticResult` — структурированная диагностика;
- `FeedbackResult` — результат подготовки feedback отдельным компонентом;
- `EvaluationCriteria` — критерии;
- `AnswerEvaluator` — интерфейс проверяющего.

### 2.3 Правила проверки

Формат проверяется отдельно от содержимого. Поля и шаги оцениваются независимо, если нет причинно-зависимой ошибки. Первичная ошибка отделяется от зависимых и независимых.

Правильное продолжение рассуждений после предыдущей ошибки получает частичную оценку (follow-through credit). Необязательные шаги не входят в обязательный итоговый балл.

Неограниченное количество отправок допускается. Каждая отправка сохраняется. Исправлять ответ можно только после получения обратной связи.

Эталон раскрывается только после завершения всего упражнения, а не после каждой проверки.

Подсказки учитываются отдельно и автоматически не уменьшают балл.

### 2.4 Идемпотентность и версии

Отправки неизменяемы. Проверка должна быть воспроизводимой для сохранённых версий упражнения, правил и evaluator. Повтор одной и той же операции не должен создавать дублирующий результат или искажать статистику.

## 3. Feedback

Feedback отделён от Evaluation.

По умолчанию пользователь видит только основную ошибку. Детали раскрываются по запросу. Полный правильный ответ доступен после завершения упражнения.

Текст обратной связи формируется на основе `feedback_key`, кодов ошибок и контекста, но не должен включать закрытые данные, не разрешённые ученику.

## 4. Learning Progress Contract

### 4.1 Назначение

Learning Progress хранит факты обучения и текущее состояние навыков. Он не выбирает следующее упражнение; это ответственность Learning Strategy.

### 4.2 ExerciseAttempt и AnswerSubmission

`ExerciseAttempt` — одна попытка прохождения конкретного экземпляра упражнения. Она может содержать несколько `AnswerSubmission`.

Статусы попытки: `STARTED`, `IN_PROGRESS`, `COMPLETED`, `ABANDONED`.

Сохраняются все отправки, результаты Evaluation, подсказки, время и версии. Метрики разделяются:

- `first_submission_accuracy`;
- `final_accuracy`;
- `submission_count`;
- `correction_count`;
- `hint_count`;
- `independent_accuracy`.

### 4.3 SkillProgress

Поля включают `user_id`, `skill_id`, `status`, `mastery_score`, `total_attempts`, `completed_attempts`, `first_attempt_accuracy`, `final_accuracy`, `independent_accuracy`, `last_practiced_at`, `last_mastered_at`, `next_review_at`.

Статусы:

- `NOT_STARTED`;
- `LEARNING`;
- `PRACTICING`;
- `MASTERED`;
- `NEEDS_REVIEW`.

Общий уровень пользователя не рассчитывается. Прогресс хранится по отдельным навыкам.

### 4.4 Оценка освоения

Освоение не определяется одной метрикой accuracy. Учитываются самостоятельность, разнообразие типов упражнений, повторяемость ошибок и устойчивость результата во времени.

Ответ оценивается по правильности; уверенность пользователя учитывается отдельно и не подменяет правильность.

Для повторного освоения требуется несколько успешных упражнений разных типов.

### 4.5 История и ошибки

`SkillProgressHistory` хранит историю переходов статуса и mastery score.

`ErrorStatistics` хранит частоту ошибок, первичность/зависимость, последнее появление и состояние исправления.

Сброс навыка разрешён, но история не удаляется.

### 4.6 Повторение

`ReviewSchedule` поддерживает типы:

- `MASTERY_REINFORCEMENT`;
- `FORGETTING_PREVENTION`;
- `ERROR_REMEDIATION`;
- `PREREQUISITE_REVIEW`.

Сначала используется простая прозрачная модель интервалов, без сложного алгоритма.

`ReviewTask` имеет статусы `PENDING`, `IN_PROGRESS`, `COMPLETED`, `SKIPPED`, `CANCELLED`. Дубликаты задач повторения не создаются.

Переход в `NEEDS_REVIEW` выполняется автоматически по настраиваемым интервалам. Повторения рекомендованы, но не блокируют обучение.

### 4.7 Зависимости навыков и сессии

`SkillDependency` используется для рекомендаций, но не является жёсткой блокировкой.

`LearningSession` поддерживает `LEARNING`, `PRACTICE`, `REVIEW`, `MIXED`.

`LearningProfile` не должен собирать избыточные персональные характеристики.

## 5. Learning Strategy

Learning Strategy выбирает следующее упражнение, его тип и сложность на основе состояния навыков, ошибок, истории и задач повторения. На первом этапе используются прозрачные правила, без ML.

## 6. Инварианты

- Успешно сгенерированный экземпляр сохраняется до показа ученику.
- Публичное представление не содержит эталона.
- Все отправки сохраняются неизменяемо.
- Исправление возможно только после feedback.
- Эталон раскрывается после завершения упражнения.
- Подсказки и правильность учитываются раздельно.
- Необязательные шаги не влияют на обязательный итог.
- Прогресс навыков независим.
- Сброс не удаляет историю.
- Review-задачи не дублируются.
- Learning Progress хранит факты; Learning Strategy выбирает следующее действие.

## 7. Тестирование

Unit: жизненный цикл попытки, метрики первой/последней отправки, partial credit, optional steps, подсказки, переходы статусов, интервалы повторения, сброс с историей.

Integration: генерация → сохранение → публичное представление → отправка → оценка → feedback → обновление прогресса → создание review task.

Security: закрытый эталон отсутствует в публичном представлении и до завершения упражнения.
