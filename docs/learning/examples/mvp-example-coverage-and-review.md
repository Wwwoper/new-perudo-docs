# Покрытие и приёмка эталонных примеров MVP S1–S9

**Статус:** проектный контрольный документ; требует продуктового согласования.

| Навык | Документ | Примеры | Основная проверяемая способность |
|---|---|---:|---|
| S1 | `s1-s5-mvp-examples.md` | 5 | применение согласованных правил и последствий событий |
| S2 | `s1-s5-mvp-examples.md` | 3 | чтение публичного состояния и отделение неизвестного |
| S3 | `s1-s5-mvp-examples.md` | 4 | подсчёт собственных совпадений и активных кубиков |
| S4 | `s1-s5-mvp-examples.md` | 6 | точная вероятность и граничные случаи |
| S5 | `s1-s5-mvp-examples.md` | 3 | проверка ограничений ставки; один пример заблокирован |

Количество примеров не является мерой освоения навыка. Оно показывает минимальное разнообразие сценариев для проверки спецификации.

## 2. Статусы примеров

Каждый пример должен иметь один из статусов:

- `DRAFT` — авторский черновик, не использовать в оценке;
- `READY_FOR_REVIEW` — условие и эталон подготовлены, требуется проверка владельцем продукта;
- `APPROVED` — правила, ответ и критерии оценки согласованы;
- `BLOCKED_BY_RULE_DECISION` — ответ зависит от неутверждённого правила;
- `RETIRED` — пример больше не используется, но остаётся в истории документации.

Примеры в пакетах S1–S9 являются проектными заготовками, а не автоматически утверждёнными заданиями. Перед включением в MVP каждый должен пройти review и получить статус `APPROVED`.

## 3. Обязательные поля карточки примера

Для согласования и дальнейшей подготовки упражнения указывать:

1. `example_id` — стабильный идентификатор;
2. `skill_id` и при необходимости `secondary_skill_ids`;
3. `exercise_type`;
4. `difficulty`;
5. `ruleset_version` и список используемых правил;
6. публичное условие и доступную пользователю информацию;
7. формат ответа и обязательные поля;
8. ожидаемый ответ либо множество приемлемых ответов;
9. критерии оценки каждого обязательного поля;
10. типичные ошибки и первичную обратную связь;
11. статус review и блокирующие решения.

Для вероятностных примеров дополнительно фиксировать режим, грань, число скрытых кубиков, требуемое количество совпадений и точную вероятность. Для S7 фиксировать источник наблюдений и ограничения выборки. Для S8/S9 фиксировать цель и допустимые компромиссы.

## 4. Общие проверки качества

### 4.1. Проверка однозначности

- Все термины соответствуют проектным контрактам.
- В условии нет скрытого допущения, необходимого для ответа.
- Эталон выводится из переданных публичных данных и согласованных правил.
- Если вывод невозможен, ожидаемый ответ явно допускает «недостаточно данных».

### 4.2. Проверка разделения навыков

- S2 не считает вероятность и не раскрывает скрытые значения.
- S3 не принимает решение о ставке.
- S4 рассчитывает вероятность, но не выбирает действие.
- S5 проверяет механику допустимости, не интерпретирует поведение соперника.
- S6 описывает историю, не приписывая мотивы.
- S7 строит ограниченные гипотезы, не подменяя ими факты.
- S8 оценивает решение относительно указанной цели.
- S9 строит условный план и задаёт триггеры его пересмотра.

### 4.3. Проверка корректности оценивания

- Правильный ответ не зависит от случайного результата раунда.
- Допустимые альтернативные ответы перечислены заранее.
- Обязательные и дополнительные поля различаются.
- Отсутствие ответа на optional field не снижает обязательный результат.
- Подсказка, исправление и самостоятельный первый ответ остаются различимыми в учебной статистике.

### 4.4. Проверка границ и отрицательных случаев

Для каждого семейства упражнений, где применимо, подготовить:

- корректный ответ;
- типичный неверный ответ;
- граничный случай;
- случай недостаточности информации;
- случай, где несколько ответов приемлемы;
- проверку отсутствия утечки приватных данных.

Не нужно искусственно создавать все категории для каждого задания. Если категория неприменима, это должно быть отмечено в review.

## 5. Сквозные сценарии для проверки границ

### X-E01. От закрытых кубиков к решению

S2 сообщает число скрытых кубиков, но не их значения. S3 считает собственные совпадения и требуемые скрытые совпадения. S4 рассчитывает вероятность для заданного режима. S8 сравнивает доступные действия по явно указанной цели.

**Приёмка:** ни один этап не получает закрытые значения; S4 не выдаёт рекомендацию; S8 не использует информацию, недоступную игроку.

### X-E02. От истории к осторожному наблюдению

S6 восстанавливает последовательность ставок и переходов хода. S7 получает только публичные события и формирует ограниченное наблюдение с оговоркой о размере и сопоставимости выборки.

**Приёмка:** `TURN_ADVANCED` не считается ставкой; S6 не присваивает мотив; S7 не превращает единичное событие в устойчивый профиль.

### X-E03. От решения к стратегии

S8 оценивает одно решение в конкретном состоянии по заданной цели. S9 использует состояние партии и результат анализа как входные сведения для условного плана на следующие раунды.

**Приёмка:** качество единичного решения не выводится из результата партии; S9 называет предпосылки и триггер пересмотра.

### X-E04. Изменение состава активных игроков

Game Domain фиксирует выбывание. S2 отображает участника в истории, но как неактивного; S3 исключает его кубики из расчётов; S6 сохраняет его прошлые события; S9 пересматривает план с учётом нового состава.

**Приёмка:** выбывший игрок не участвует в текущем TurnOrder и расчётах, но не удаляется из истории.

## 6. Блокирующие вопросы перед утверждением

| Решение | Какие примеры затрагивает | Условие разблокировки |

| Полная таблица переходов ставок | будущие S1/S5 и часть S8 | утверждённая таблица допустимых повышений с примерами границ |

| Приёмка плана S9 | S9 и смешанные сценарии | утверждённый минимум: цель, предпосылки, ветви и триггер пересмотра |
| Критерии MASTERED | Learning Progress | отдельное решение по повторяемости независимых результатов для каждого навыка |

## 7. Условие готовности примеров к передаче

Пакет эталонных примеров готов к передаче команде реализации, когда:

- все MVP навыки имеют хотя бы один `APPROVED` пример;
- заблокированные примеры исключены из выдачи и оценки;
- для каждого approved примера проверены условие, эталон и критерии;
- сквозные сценарии не нарушают границы модулей;
- открытые решения явно перечислены и не замаскированы предположениями;
- продуктовый владелец подтвердил формулировки и UX-ожидания.

Этот документ не утверждает примеры автоматически и не заменяет утверждение правил.
