# План валидации эталонных примеров MVP S1–S9

**Статус:** процедура проверки; результаты должны фиксироваться в `mvp-example-review-register.md`.

## 1. Цель

Проверить не только наличие эталонного ответа, но и то, что пример:

- корректен относительно утверждённого Game Domain;
- решается только по данным, доступным пользователю;
- имеет однозначные обязательные критерии;
- допускает заранее описанные альтернативы;
- корректно обрабатывает неполные, граничные и ошибочные ответы;
- не приписывает навыку обязанности соседнего навыка.

Этот план не утверждает существующие примеры. До прохождения review их статус остаётся `READY_FOR_REVIEW` или `BLOCKED_BY_RULE_DECISION`.

## 2. Набор проверок для каждого примера

| Проверка | Что подготовить | Условие прохождения |
|---|---|---|
| V-01 Correct | Один полный корректный ответ | Все обязательные критерии получают PASS |
| V-02 Incorrect | Типичный неверный ответ | Ошибка обнаруживается нужным критерием и получает правильную диагностику |
| V-03 Partial | Ответ с частью обязательных полей | Сохранены результаты отдельных критериев; пропуск не превращается в PASS |
| V-04 Boundary | Ближайшее применимое граничное состояние | Ответ соответствует явному граничному правилу |
| V-05 Alternative | Второй допустимый ответ, если задача допускает выбор | Допустимый вариант принимается без требования совпадения с одним текстовым эталоном |
| V-06 Insufficient | Сценарий с недостатком данных, если применимо | Принимается корректное указание недостаточности данных |
| V-07 Privacy | Проверка публичной части условия | Ни одно закрытое значение не влияет на доступный ответ незаметно для ученика |
| V-08 Outcome independence | Изменён случайный исход после принятия решения, если применимо | Оценка решения не меняется задним числом |

Неприменимые проверки помечаются `N/A` с коротким обоснованием. Нельзя отмечать `N/A` только потому, что для проверки не подготовлен fixture.

## 3. Навыковые проверки

### S1 — правила и механика

- Проверить каждую роль и последствие Dudo отдельно.
- Проверить различие потери кубика и выбывания.
- Проверить выбор следующего активного игрока при выбывании проигравшего.
- Palifico-проверки запускать только для явно утверждённых состояний и правил.
- Не включать проверку перехода ставки до утверждения таблицы переходов.

### S2 — восприятие стола

- Скрытые значения отсутствуют в learner-visible payload, а не только визуально замаскированы.
- Число скрытых кубиков и публичные ставки совпадают с состоянием сценария.
- Первая ставка не получает искусственную предыдущую ставку.
- Положение участника на экране не меняет его идентичность.

### S3 — подсчёт

- Пересчитать собственные совпадения вручную по каждому режиму.
- Проверить `required_matches = max(0, bid_quantity - own_matches)`.
- Для обычной ставки на грань 2–6 учесть единицы; для ставки на единицы считать только единицы.
- В Palifico не учитывать единицы как джокеры.
- Выбывшие игроки не входят в количество активных скрытых кубиков.

### S4 — вероятность

- Проверить исходные `n`, `p`, `k` и смысл события (`exactly` / `at least`).
- Независимо пересчитать дробь точной арифметикой.
- Проверить сокращение дроби и дополнительное десятичное представление, если оно показывается.
- Проверить `required_matches = 0` и `required_matches > hidden_dice`.
- Не переносить вероятность обычного режима на Palifico.

### S5 — механика ставок

- Проверить общий верхний предел по активным кубикам.
- Разделить правила подсчёта совпадений и правила перехода от ставки к ставке.
- Любой пример перехода должен ссылаться на конкретную утверждённую строку таблицы.
- Не оценивать заблокированные переходы.

### S6 — история торгов

- События сохраняют исходный порядок.
- `BID_PLACED` учитывается как ставка; `TURN_ADVANCED` — только как смена хода.
- Неполный фрагмент не выдаётся за полную историю раунда.
- Резюме не может содержать больше ставок, чем доступно событий размещения.

### S7 — анализ соперников

- Каждое утверждение классифицируется как наблюдаемый факт, гипотеза или вывод при недостатке данных.
- Проверяется размер и сопоставимость выборки.
- Альтернативные объяснения не ранжируются без критерия и данных.
- Закрытые кубики не используются для построения learner-facing вывода.

### S8 — принятие решений

- Законность действия оценивается отдельно от качества обоснования.
- Цель и критерии сравнения видны до ответа.
- При нескольких приемлемых вариантах evaluator принимает каждый вариант, удовлетворяющий рубрике.
- Случайный исход не меняет оценку качества решения.

### S9 — стратегия партии

- План содержит цель и предпосылки.
- Условные ветви опираются на наблюдаемые изменения состояния.
- Триггер пересмотра можно определить по игровому событию или состоянию.
- План не обещает конкретные случайные броски или действия соперников.

## 4. Проверка эталонов S4

Для уже записанных S4 примеров независимые контрольные значения:

| Example | Событие | Контрольный ответ |
|---|---|---|
| S4-E01 | Ровно 2 из 4 при p=1/3 | 8/27 |
| S4-E02 | Не менее 2 из 4 при p=1/3 | 11/27 |
| S4-E03 | required_matches = 0 | 1 |
| S4-E04 | 4 требуемых при 3 скрытых | 0 |
| S4-E05 | Не менее 1 единицы из 3 при p=1/6 | 91/216 |
| S4-E06 | Не менее 1 выбранной грани из 2 при p=1/6 | 11/36 |

Эти значения уже приведены в эталонном документе и повторены здесь как контрольный лист. Их повторное включение не является независимой математической верификацией; reviewer должен выполнить отдельный пересчёт.

## 5. Запись результата

На каждый пример фиксировать:

- `example_id`;
- версию публичного условия и expected answer;
- версию ruleset и evaluator;
- идентификаторы проверочных ответов V-01…V-08;
- исход каждого теста (`PASS`, `FAIL`, `N/A`, `BLOCKED`);
- обнаруженные дефекты и их severity;
- reviewer и дату.

Пример нельзя утвердить при любом применимом `FAIL` или `BLOCKED`. После исправления условия или эталона затронутые проверки выполняются повторно.

## 6. Критерии завершения ревизии

Ревизия завершена, когда каждый пример из review register имеет заполненный протокол, блокированные варианты отделены от scored MVP, а сквозные сценарии X-E01–X-E04 пройдены повторно. Итогом является обновлённый статус в реестре, а не устное предположение о готовности.
